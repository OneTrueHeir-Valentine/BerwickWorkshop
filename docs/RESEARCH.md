## Findings

### Growth bracket (confirmed in part)
Source: [ベルウィックサーガのレベルアップ, 西へ東へ](https://west-east.blog.jp/archives/2718403.html) (player blog, older post).
- A stat grows toward start value + growth rate x levels gained, and a correction keeps the result within a band around that: strong ±1, medium ±2, weak ±3, none (no limit).
- The post says Daoud and Lynette are the only characters with no correction, and Reese's HP correction is weak.
- On the disc, growth record byte 2 bits 5 to 6 hold 1 for exactly Daoud and Lynette, and 2 for Reese. So 1 = none and 2 = weak (±3) match. 3 is a tighter band, ±1 or ±2 not yet known. The post says corrections are per stat, but the record has one value per character; the rest of byte 2 and byte 3 are other data (byte 3 repeats the character's class ID).
- Credibility: single player source, consistent with two independent disc facts.

### Formulas (published, not yet located in code)
Sources: [EmblemWiki, Berwick Saga Calculations](https://wiki.serenesforest.net/index.php/Berwick_Saga_Calculations); [銀の意思流攻略, 命中率と攻撃力](https://www.silver-intention.com/Game/BerwickSaga/System-5.php).
- Accuracy = weapon precision x 10 + weapon skill + bonuses. Avoid = attack speed x 2 + terrain (x 2 at range 2+). Attack speed = speed minus (weapon weight + shield weight minus strength / 2, not below 0).
- Critical rate = weapon critical + (weapon skill minus 50, not below 0) + bonuses; critical damage adds random 10 to 20.
- Equipment failure = 5% per weapon rank above level (7 levels of slack with Advanced). Injury base 9 for knives, 3 otherwise. Experience per kill = enemy class experience + modifier (class experience is the class field we already decode and edit).
- Credibility: two independent wiki and guide sources agree on accuracy.

They are encrypted CodeBreaker codes, so their real addresses are not readable yet. ### Program locations from the decrypted codes (static analysis, 2026-11-12)
The 2005 codes are Pro Action Replay 2 codes using the standard Action Replay 2 encryption (default seed `05100518`). Decrypted with a local port of Omniconvert's routine (GPL-2.0, not shipped). Decryption is confirmed by two money codes that decode to `0x01EC52E4` and `0x00DBEEF4`, the same town and battle gold addresses found independently in the note.com article.

Both executables have the same layout (one load segment; program address = file offset + `0xFFF00`) and only 12,258 bytes differ. Every location below is byte-identical in the Japanese and English executables.
- `0x0013A740`: random integer in a range (stream, minimum, maximum). Called from 206 places, so it marks every random roll in the game.
- `0x0013A7E0`: percent roll. 66 call sites; two are followed by 50% checks.
- `0x00174A90`: add to a unit attribute and clamp it to a hard-coded per-attribute cap (caps seen: 15, 20, 30, 50 or 100, 199, 999, 100000). This is where stat and experience caps live. Which index is which stat is not mapped yet.
- `0x00224570` to `0x002245A0`: experience gained after battle is added here (attribute 2). The old "always level up" code forced this amount to 100, and the experience multiplier code shifted it left.
- `0x002274DC` to `0x002274EC`: Parry skill roll (first labelled as the shield roll; corrected 2026-11-12): a random 0 to 99 compared against the parry rate at offset 0xA0 of the battle unit, which `0x00177EC0` builds from weapon level and needs the Parry skill. Success cancels the hit.
- `0x0022CE0C`: a rate formula that subtracts 50, then subtracts 50 or 75 and halves. Not identified yet.
Live confirmation (PCSX2 2.9.78, English v2.3, first battle, memory read and written over PINE):
- All seven locations above hold exactly the executable's code while the game runs (8 words each), and 395 of 400 random words across the program match the file (the rest are data that changes during play). The code is not relocated, so changes written into the executable on disc land where expected.
- Parry roll confirmed: changing the branch at `0x002274EC` so the failed-roll path is never taken made every unit parry every attack.
- Experience gain confirmed: replacing the instruction at `0x00224580` so the gained amount is 100 made a unit level up after one fight.
- Both changes were temporary (emulator memory only) and were reverted.

### Stat caps (static map plus two live tests, 2026-11-12)
- The attribute add routine at `0x00174A90` uses a 15-entry jump table at `0x004A4060` (same in both editions). The unit record in memory has the disc starting-record layout without its 4-byte tag, and the cases map to: HP bonus (cap 50), Strength, Agility, Defense and Mind bonuses (cap 15 each), Luck (cap 20), level (cap 30), and experience (cap 199, 100 at level 29, 0 at level 30). Five indexes are not identified.
- Live units in memory (English v2.3, first chapter): a starting copy from `0x01E13C8C` (stride 0x234) and the current army from `0x01E17F9C`; all decoded fields match the game.
- Live test 1: with all six stat caps in this routine set to 0, a level up still raised Strength.
- The add-and-store routine `0x00174550` (table `0x004A4020`, writers in `0x004A3FE0`) holds a second copy of the same limits and is the one level ups call. Live test 2: with both copies at 0, a level up raised nothing. Both copies together are the stat limits; offered as rules in v0.11.0.
- Next lead: the level-up code after `0x002245A0`; level and experience caps still need their own tests. The second limit routine and its tables are already mapped above.

### Movement (2026-11-12, confirmed in a running game)
- Movement type is an 8-bit field in the class record starting at byte 6 bit 1 (the program loads the halfword at offset 6 and keeps bits 1 to 8). Values: 0 cavalry, 1 horseman (light cavalry), 2 flying, 3 knight, 4 armor, 5 infantry, 6 thief, 7 civilian, 8 special (ballistician), 9 snow, 10 war priest, 11 fighter (light infantry), 12 priest, 13 unused by any class. Original classes use 0 to 12.
- Mount state is class record byte 3, bits 4 to 5: 0 on foot, 1 mounted, 2 flying. It agrees with the movement type for every class on both discs.
- Terrain cost table: in DATA3.DAT, two identical copies. English `0x00CCE128` and `0x08ECB3FC`, Japanese `0x00CD7928` and `0x08EB3BFC` (header start). Header: terrain count 64, type count 14 (two 32-bit values). Then 14 rows of 68 bytes: byte 0 mount state, byte 1 unknown (7 7 6 4 3 4 4 3 2 4 3 4 3 7), bytes 2 and 3 zero, bytes 4 to 67 the cost of terrain kinds 0 to 63 in tenths of a point; 255 means it cannot be entered.
- Earlier searches missed it because the costs are stored as tenths (forest for cavalry is 40, not 4). The rows match the gamekouryaku.com terrain list (snow forest is terrain 50: 7 6 1 4 4 4 3 2 3 3 2). Terrain names are not stored as plain text, so kinds are named by the published row they match.
- Program: the class table pointer is at gp minus 0x7B88 (`0x004B4768`, gp `0x004BC2F0`); class IDs count from 1 with 100-byte records. `0x0017CEB0` returns a unit's movement type; `0x0017CF20` returns a class's cost row from the table pointer at `0x004B4784`.
- Live tests (PCSX2, English v2.3, first battle): all enterable terrain set to 4 shrank every movement area; class 0x01 set to Flying let Reese move as a flier; open ground at 1.5 limited Move 4 units to 2 hexes. So the table, the class field and tenths all work.
- Old cheat code pages (atwiki, archived) list program patches for Canto on any unit and full move after moving; leads for the speed prototypes.

### Damage and shields (2026-11-12, program reading plus live tests)
- Battle setup `0x0022B940` fills one record per combatant: 0x54 attack, 0x6C physical defense, 0x70 magic defense base, 0xA0 parry rate, 0xA4 shield block chance (`0x00177C70`: shield accuracy + shield level, +18 with a skill), 0xA8 shield Might (item Might bits), 0xAC shield magic reduction, 0xC0 hit, 0xC4 critical. Shield values count only for a shield that is not broken and whose size the class can use (class byte 0x1B).
- Damage routine `0x0022A2D0`: damage = attack - defense - reduction (never below 0), plus a magic part for weapons that deal both; a critical hit adds a random 10 to 20. The reduction is the shield's Might on a successful block, a weapon guard skill, or a fixed 10 from another skill (only one applies).
- Shield block roll: branch at `0x0022A638`, tried only when the hit would do damage, the defender has a usable shield and no other guard applied. Knives (item type 0) and two weapon effects cancel the block afterwards. A reduction above 0 triggers the block animation and durability use, so a passive bonus must go into defense instead.
- Shield guard prototype: `0x0022A640` to `0x0022A6A4` rewritten in fewer instructions with the same success behaviour; a failed block (physical attacks) adds Might >> n to defense. The forecast uses the same routine with fixed rolls, so it shows the guard.
- Static review correction: guard applies after a failed block roll, not after a successful roll canceled later by a weapon effect. Knives follow the type-0 path to `0x0022A940`, which clears physical defense, including the guard bonus. Shield block Always does not override shield-bypassing attacks. The earlier promise of guard against knives was incorrect; v0.14.1 corrects the descriptions without changing the instructions.
- Live tests (PCSX2, the user's test export, with parry forced off in memory): Leon (attack 15) against a Deserter (defense 2, Verian small shield, Might 4). Prototype at full Might: an unblocked hit did 9. Original code: a blocked hit did 9; unblocked hits normally do 13.

### Weapon and shield training (2026-11-12)
- `0x0017A900` raises a weapon level (unit, type 0 to 13, amount), capped by the class cap; types 11 to 13 are the small, medium and large shield. Weapon levels sit three per 32-bit word with a 2-bit check value in the top bits, which the game rewrites on every change.
- `0x0022B2C0` grants battle training: mode 0 after an attack (step 1, `0x001716C4`), mode 1 for shields (step 4, `0x001716A4`), mode 2 (step 2) from another caller. Shield training is granted at `0x00228070` only when a block roll happened: block success, or a failed block on a hit.
- Amount (`0x001716D0`): nothing with 0 growth; at level 20 and above a failed attempt gives nothing (`0x00171760`); one or two rolls (two below level 10) plus one on success; each passes when random < growth × 10 and random < 190 − 3 × level, adding one step. Capped at the class cap.
- Vantage: a defender that kills its attacker first never gets a block roll, so it gains no shield training. The Vantage decision is made once per battle at `0x00224E50` (flag at battle +0x11A8, skipped in forecast mode +0x11D8). At `0x00224E68` to `0x00224EF4` an inlined battle-event push duplicates the routine at `0x0022E1E0`; calling that routine frees 20 words, enough to grant the defender one shield training event through `0x0022B2C0` (mode 1) when its shield Might (+0xA8) and cap (+0x10C) are above 0. Live test: with blocks forced to fail and the cutoff on, Ward's medium shield went 30 to 40 when Vantage triggered.
- Live tests: shield step 4 changed to 50 made a shield level jump after one block; weapon step 1 changed to 50 made a weapon level jump after one attack.
- Class record byte 0x1B bits 4 to 6 are the shield sizes a class can use (small, medium, large); they agree with the class's shield level caps for all 217 classes.
- Critical bonus: Random(1, 10, 20) at `0x0022AEE4` to `0x0022AEF0`; the range routine loops forever if the high value is below the low one. Live test: forced criticals with 30 to 30 added exactly 30.
- Failed-attempt cutoff: `slti at, a1, 2` at `0x00171760` (rank below 2, level below 20). Live test with the growth check forced: a failed block at shield level 25 trained once the cutoff was lifted.
- Experience: `0x00224230` handles the experience kinds. Battle experience is added only after a defeat: `0x00174050` takes the enemy class experience value (class byte 4) plus the level difference table at `0x00429F10` (16 words, enemy level minus own level from -8 to +7: -40 to +15), then `0x00173D50` adds 20% with skill flag 0x40000 and item percentages, clamped 0 to 100 (`0x0017410C`, `0x00174124`). Staff kind: staff level + 6 (`0x00224394`) + Random(0, 3) - level / 5. Live test: with the table all 50 a defeat gave exactly 50 (that enemy class has experience 0).
- Terrain effect table: DATA3 terrain cost table + 0x420, both copies, both editions. Count 64, then 24 bytes per terrain: +0 avoid (matches the published list; live test: plain set to 50 showed 50%), +0x10 recovery while resting in percent (poison swamp -20), +0x14 flags. Flag 0x40 keeps flying classes from stopping (`0x001AB610` and copies, enemy movement and mount change checks); set on buildings and a few other kinds. Live test: with it cleared, a flying class ended its move on a house.
- Skills: check routine `0x0017D1F0(unit, flag)`; skill index i uses flag 1 << i below 30, 0x80000000 | 1 << (i - 30) below 60, 0x40000000 | 1 << (i - 60) below 90 (the skill list skips two unused bits per 32). Every check site is listed by `..\berwick-decomp\skillsites.py`. Iaido (`0x00229E7C`) and Knock Away (`0x002278B8`): half the weapon level plus 40 or 30. Banes: attacker hit rate capped at 33 (`slti` and `addiu` pairs from `0x00227550`). Live test: Iaido, Knock Away and a bane fired with the chances raised; Robust and Robust+ are silent passives, and the roll beside Robust+ (`0x00226188`) is for units without it.
- Pursuit (`0x00225488`, `0x002254E8`): an extra attack when attack speed (+0x7C) leads by 5 or more. Shieldfaire: block chance + 18 (`0x00177E58`). Paragon: amount x 0x66666667 >> 33, a fifth (`0x00173DC0`, `0x00173DC8`, `0x00173DDC`); other shares come from other multipliers and shifts. All three checked live.
- Parry chance `0x00177EC0`: (weapon level + 10) / 2 (`0x00177F50`) with the Parry skill, plus an item effect. Block chance `0x00177C70`: shield accuracy + shield level + 18 with Shieldfaire; the +10 at `0x00177E88` never applies (its test `0x0016B4F0` always returns 0). Training `0x001716D0`: chance 190 (`0x001717A4`) - 3 x level, clamped 0 to 100, and a second roll under growth x 10. Live test: Parry with bonus 200 parried every hit; ceiling 0 stopped all training.
- Hit and critical: battle setup `0x0022B940` stores attack speed +0x7C, hit +0x80 (`0x00179620`), avoid +0x88 (`0x00179D30`), crit +0xB4 (`0x00179250`), crit evade +0xBC (`0x00179100`); final hit +0xC0 = hit - enemy avoid, crit +0xC4 = crit - enemy crit evade. Avoid = attack speed x 2 (`sll` at `0x00179D68`) + items + terrain (doubled at range 2 or more, `0x0022BFE4`, `0x0022BFF8`). The Critical skill adds the unit's level. Live test: x 4 raised avoid. The situational bonuses come from active skills, which set one-shot bits in the unit state word copied to battle +0x4C: Aim +33 hit, Focus Chant +30, Desperation +22 and no defense, Throw +10, Deadeye -15, Sunder +25 critical, Pulverize double attack. Sunder and Desperation checked live. The equipment window shown while choosing a command has its own copy (addiu v0,v1,N): Aim `0x00389C88`, Sunder `0x00389CB0`, Deadeye `0x00389CD8`, Throw `0x00389DA0`, Focus Chant `0x00389E28`, Desperation `0x00389E70`.
- Item record bonus fields (old editor offsets, checked against the disc: bracers, rings, scales, elemental shields): defense byte 12 (6 signed), agility 13 bit 3 (5), avoid 14 (8), hit 15 (8), mind 16 (5), strength 16 bit 5 (5), fire 17 bit 6 (6), thunder 18 bit 4, wind 19 bit 2, dark 20, holy 20 bit 6, critical evade 21 bit 7 (8). Effect flags bytes 28 to 39; bit 21 is checked by the command menu after moving (ballistae only).
- Command waits: 0x001C34A0 stores a wait per command (Astra 6, Focus Chant 6, Triple Shot 4, Double Shot 3, One-Two 5, Evasion 4, Imbue 3, Flourish 3, Silence 9) in the unit state bytes +0x60.., counted down per unit turn by 0x001B6F10. Steal, Robbery and Mug II share a count per map (unit state +0x105 bits 2 to 3, lowered at 0x001DF1BC). Swimmer: movement cost builder 0x001BA870, mount state 0x0017DFB0.
- Archives and event scripts (v0.28.0): DATA4.DAT from byte 368 lists the top-level archives (12 bytes: word, sector in DATA3.DAT, size). Archives are TARC (count, name list offset, 12-byte entries: offset x 2 + compression flag, size, word). Compression: Berwick LZ (output size, stored size, control bits; literal, short copy up to 256 back, long copy 13-bit). Event scripts e0000001.dat..e0003986.dat (3983 files) in the 20-file archives near the end of the index; same layout on both discs. Script record: size, command, argument sizes, arguments as nested records; 1 number, 2 text, 3 local value, 4 assignment, 5 event (0, local count, body size), 6 if, 7 while, 8 and, 9 or, 0x0A..0x0E + - * / %, 0x0F..0x14 == != >= > <= <, 0x15 negate, 0x16 not, 0x17 break, 0x18 run event, 0x2C wait frames. Handlers read with Ghidra 12.2 and the EE processor extension.
- Command menu `0x0038B400` to `0x0038CB00`: action state +0x2C bit 1 means the unit has moved. Move-limited commands test it with andi 1 (Aim, Deadeye, Sunder, Pulverize, Overwatch, Axe Guard, Windsweep, Battle Cry, Steal) or a 0x4283 mask (Hurry, Provoke, Evasion, Silence, Imbue); open commands use 0x4282, 0x282 or 2 (Double Shot, Triple Shot, Astra, Focus Chant, Guard, Search, Return, Convert); Throw, Mercy, Desperation, Flourish and Deathmatch after a move ask the weapon (item property 0x15). Allowing Hurry after a move gives endless movement. Checked live for Aim, Deadeye, Sunder, Battle Cry, Evasion, Provoke (allowed) and Desperation, Astra, Guard, Search (blocked).
- Tamper checks: a unit check (`0x00183540`, stats and weapon-level check bits) and a program checksum (`0x00125E60`) both set a marker (`0x00506E64`) that is copied into save data. Program rules trip the program check. No effect of the marker has been seen in play yet. Starting records on the disc carry no weapon check bits, so editing them is safe for the unit check.

### Stable prices (2026-11-13, script and town-overlay trace)

The stable uses event `e0000602.dat`, not the item table's base price. Event 601 builds the purchase list; event 600 obtains stock from event 603 and price from event 602, then calls command `0x4A6` with horse ID, stock and price. In the saved English town overlay, the handler at `0x0053F9D0` passes those arguments to `0x00551DE0`, which appends a 0x44-byte menu row. The price is the row's third word. Rendering at `0x00551920` and the affordability check at `0x00551590` read that same word.

Event 604 also calls 602 for the purchase amount. Event 598 uses that result for its funds check (`0x127`) and payment (`0x126`), then event 605 equips the horse and decrements its stock. Thus the event price is used beyond the displayed menu.

Verification: direct extraction from both owned ISOs, Ghidra call tracing, and comparison with three rows in the existing English stable RAM dump (Thin 1000, Plain 2500, Tough 8000). No new live patch or purchase test was performed. Town-overlay addresses were traced in the English snapshot only; matching event data does not prove Japanese overlay addresses. A price editor still needs compression and archive-size handling, all-copy export verification, and an in-game display/payment test. Earlier searches missed these values because the price assignments are separated by 100-byte script blocks.

Writing (v0.29.0): BerwickLz.Compress encodes literals, short and long copies, and must end with the game's end marker: the decompressor at `0x0013C268` has no output count and stops at a long copy whose length byte is 0 (every original file ends with `00 00 00`, after a fresh control byte when needed, and the header's second word counts it). A first test disc without the marker hung the game at the stable. ArchiveEditing replaces a compressed child in place when the new data fits its recorded size; the entry's third word is a name hash and stays unchanged. Checked in PCSX2: Thin Horse at 1234 showed in the menu and the shopkeeper's line, and buying it took exactly 1234.

### Starting unit data, bags and partners (2026-11-13, program reading)

The starting unit table is a stream of tagged blocks read by `0x00181C60`: `HIST` (allocates history), `UNIT` (the record), `ITEM` (inventory list), `SACK` (bag contents), `FAVP` (partners, 12 bytes copied to unit +0xA4), several 100-byte `CP21`-style blocks (unit +0x80 to +0x9C) and `ENDC`. Unknown tags are skipped four bytes at a time.

- `SACK`: inventory slot of the bag item, item count, then one 8-byte entry per item in the inventory slot layout. On both discs only Reese (2 x item 0x21), Sherlock (3 x Bronze Arrow) and Christine (4 x Vulnerary) start with contents; the block sits right after the character record (record offset + 0xFC). Its size is fixed, so entries can be changed or emptied in place.
- Partners: `ufavor.dat` in basedata.ar, 17 rows of 34 bytes (16 used): character ID, then four entries of partner ID, bond value, flags byte. Both copies sit 0x244 bytes before each item table copy (EN `0x0CB71C0`, `0x08EB4494`; JP `0x0CC09C0`, `0x08E9CC94`); both editions identical. The growth record's word at +6 picks the row. `0x00173B10` copies partner IDs and flags into the unit's partner block every time units are loaded (keeping the progress bits 0x11 per partner), and `0x00173C80` returns the bond from the table unless flag 0x10 is set. Only characters with a `FAVP` block (the same 16) can hold partners.
- Partner bonus: `0x001B8430` sums bond / 10 for each partner within 2 spaces that can act. Hook 0x30 (`0x001B7F70`, inside hit `0x00179620`) adds the sum to hit; hook 0x38 (`0x001B79D0`, inside critical `0x00179250`) adds the sum / 5. The hook table at 0x523340 is filled by `0x001B7580`.
- Script variables 0x170 to 0x17F read partner slot state (enabled, ID, bond, flag bits 1 and 2); 0x170 to 0x173 toggle flag 0x10.
- Command 0x14D (`0x00269C20`) weights 2000/1500/1200/1000/500 are a unit sort order, not fees.

### Mercenary fees and script command names (2026-11-13)

- Top archive 16 in DATA3 is a leftover developer memory dump (ELF core, `MWDump.Memory`). It holds the script command names in registration order: `PredefinedEmpty` is command 0, `PredefinedLiteral` 1, `PredefinedAssign` 4, and so on, matching the decoded format (0x1D7 is `GetItemPrice`, as traced earlier). The full list is kept with the research files, not in the product.
- Mercenaries: command 0x1C0 `GUnitCalcMercenaryCost` calls `0x00170480`, which looks the unit up in an 18-row table at `0x0042D450` (24 bytes per row: character ID, flags, base fee u32 at +8, fee per level s16 at +12, then values at +14 and +16 and a hash word). Fee = base + (level & 0x3F) x per level; when that is 0 and unit byte +0x46 is set, that byte x 100 (Saphira has 0 and 0); halved when the script asks for it or a unit flag is set. `0x00171DD0` returns 70 % of the fee and `0x0017E360` the plain fee. Identical in both editions.

### Armies and bosses (2026-11-13)

- Every map's units are in `team.dat` (uncompressed) inside `udNNN.ar` in a top archive, with a loose copy of the same file as the next top archive. 532 files, 276 distinct, 3078 unit blocks; identical between editions.
- A unit block is the tag `UNIT` plus the starting-record layout (name ID at +12 and +14, class at +19, level at +20, bonuses, weapon levels from +36, skills at +56), then zero words the loader skips, then `ITEM`, a count of 8 and 8-byte item slots (item, uses, flag 0x80 at slot +3 = dropped when defeated). The `ITEM` tag sits between 0x90 and 0xB8 depending on the block.
- Unit names: `namene.ar` (top 14) holds `un001` to `un1566`, glyph numbers (0 to 25 capitals, 26 to 51 small letters, 0x34 to 0x3C digits 1 to 9, 0x3D zero, 0x44/0x45 brackets, 0x46 hyphen, 0x47 apostrophe, 0x50 space). The Japanese disc uses the same numbers for Japanese glyphs, so the English names ship as reference/units.csv. Bosses are units whose name ID occurs once in their army (Baldur in army 380, Murtagh in 376).

### Furniture prices (2026-11-13)

- The developer memory dump also lists event script names in event order: the name's position minus 530 is the event number (`city012_get_horse_price` = 602, `get_horse_vidx` = 603, as traced before). `get_furniture_price` = event 727, `select_buy_furniture` = 729, `town_map27_kaguya` (the furniture shop) = 730.
- Event 727 returns the price for furniture numbers 1 to 5 and 7 to 14 (number records at 0xA0 + 88 per piece, each after the comparison with the piece number). Piece n is event item n + 1 (names in `sysfont.ar` `evitem002` onward; checked against the shop list in a running game): Sword Mount 23,000, Big Rug 19,000, Porcelain Vase 25,000, Deer Mount 26,000, Coat of Arms 27,500, Coffers 30,000, Tapestry 45,000, Bird Statue 17,000, Art "Revival" 22,000, Maiden Statue 42,000, Treasure Chest 36,000, Art "Hope" 14,500, Luxury Bed 32,000. The purchase (event 729) charges this price; the shop list (event 730) shows fixed menu texts 91 onward with the original prices written into them. Identical in both editions.
- Event 727 shares archives with event 602 (ev_all.ar), so edits to both are written into each archive together (`ScriptPrices.Combined`).

### Stat getters (2026-11-13, static, for editable formulas)

- `0x00180BF0(unit, n)` returns a base stat (class base + the unit's bonus, halved under a status flag): 1 HP (capped at 100), 3 Strength, 4 Agility, 6 Defense, 7 Mind, 8 Move x 10, 9 a class value at byte 7, 10 level x 5, 12 level, 13 and 14 experience fields. Each caller passes n as a constant, so the stat a formula reads is one immediate.
- Wrappers that add equipment and skill bonuses: `0x001800B0` (Strength, called with flag 1 by the attack routine `0x0017BEE0` for physical attacks), `0x0017F8B0` (Mind, used for magic attacks), `0x0017E8B0` (Agility), `0x0017F0B0`/`0x0017F0C0` (Defense), `0x001808B0`/`0x00180A70` (HP). Thin wrappers: `0x001808A0` (Strength), `0x001800A0` (Mind), `0x0017F0A0` (Agility). The status screen `0x0018F610` reads all of them.
- Plan: per formula, offer the stat as a choice by changing which wrapper the formula calls (jal target) or the getter index, then check each in a running game.

### Item slots (from the discs)
- 156 catalogue entries are unused placeholders, in runs inside each weapon category (for example 0x017 to 0x01F among knives). Their records hold template data; 19 are byte-identical to a real item. None are starting items. Shops, chests and drops have not been mapped, so a placeholder could still be referenced by chapter data.

## More skills read from the program
- Fortune `0x00174DC0`: has Fortune (or an item with effect 0x2C) unless unit state +0x5C has bit 27 or 31; the battle code at `0x0022C66C` then clears the real critical chance (+184) and +196 of the attacker's side. The forecast value (+180) is left.
- Camouflage: terrain avoid times 3, halved, in the forecast hooks `0x001B7B74` and `0x001B7DAC` and in battle `0x0022C040`. Checked live: Ward on plain 11 avoid at 2.5 times, 8 without.
- Hunter `0x0022BF88`: bow, crossbow or ballista (`0x0016E4A0`, weapon types 8 to 10) against a defender on terrain class 4 or 5 sets the defender's terrain avoid to 0.
- Hateful `0x002F2F7C`: when attacked, status 15 (Provoked) for 10 aimed at the attacker, the same call as the Provoke command (`0x002F23E4`). Status n: unit state +0x5C bit n, counter byte +0x60 + n, set by `0x001B7400`.
- Acrobat `0x001BA89C`: every enterable terrain costs what terrain 0 costs, except terrain 63 and terrains with attribute flag 0x80 (buildings and kind 29). Swimmer does the same for flag 0x100 (water).
- Celerity skips the class list at gp-31600 (gp 0x4BC2F0), which holds exactly the 36 mounted classes.
- Armsthrift `0x0016D2D4`: adds 20 to the chance that a weapon use costs no durability. Checked live at 100.
- Slow Start: the move left at the start of a move (unit state +0x3C) is Move minus 10 tenths minus what is spent, at twelve places in `0x002F33B0` to `0x00300680`; the Move stat itself is unchanged.
- Watchful: hidden units are uncovered within 3 hexes instead of 1 (`0x001BDF3C`), and the map view is refreshed over 3 hexes (`0x001ACF48`). Obfuscate `0x001C4B50` hides stats until unit state +0x58 bit 17 is set.
- Despoil `0x003F97EC`: after a kill, the side gains enemy level times 4 (`0x003F98BC`) plus random 0 to 50 (`0x003F98AC`) through `0x001B94D0` (gold at army +68, capped at 999,999). Checked live: +160 for a level 5 enemy at 32 per level and no random part.
- Cavalry moves with the horse when horses change hands (`0x001E4B90`), and `0x00172AE0` gives the horse type from the mounted class list.
- One-Two sets status 4; choosing it stores a wait of 5 (`0x001C35DC`), and after the fight `0x0022D524` sets the counter to 6, which is the one that counts. Checked live at 1.
- Checked live by lending the skills: Prepared (Elbert, Longsword held, countered an archer 2 hexes away with a Pilum carried third; its check was not found by the mask scan), Versatile (a Cleric healed and kept Aura first), Hurry (8 hexes with Move 7), Swap Horse, and Canto moving on after an attack. Locktouch, below.
- Locktouch: `0x001B9D20` is true when the unit has skill mask 1 or carries a Door Key (item 465); the action menu (`0x0038C224`) then offers Open (command 569) when a gate or door object is next to the unit. Opening (`0x001DEA14`) uses up a Door Key only when the unit lacks the skill. A map event spot of menu kind 9 offers command 568 to a unit with the skill standing on it (`0x0038CF5C`). Checked live in story battle 9: Leon, given the skill and no key, was offered Open next to a gate and opened it.
- Watchful range checked live (quest 6 map): an enemy archer given Hide in a forest, 4 hexes from Leon with Watchful, showed with the range set to 6 and hid again after the next refresh with 3.
- Silence wait: `0x001C365C` (9) is only the value stored when the command is chosen. After the command runs, `0x001DF670` sets status 1 of the second status set (bits at unit state +0x80, counter at +0x84 + n, setter `0x001B7330`) to 10 (`0x001DF674`), which is what counts, as with One-Two. Checked live: set to 2, Leon's counter read 1 right after use and Silence returned two turns later. Another path (`0x00203740`) stores 7 into the same counter; not traced.
- Script command names: top-level archive 16 is a program file (ELF, identical on both editions) holding the game's name for each of its 0x4EF script commands, in order from "PredefinedEmpty" (command 0), NUL-separated with padding. The Events page reads them from the opened disc (ScriptText.ReadCommandNames).
- Mission and quest titles: entries mission001 to mission015 and quest001 to quest218 (quest numbers follow the order of the quest records) in top-level archive 549 on the English disc, in the unit-name font (16-bit glyphs: capitals 0, small letters 26, digits 0x34, then . , ! ? : at 0x3E to 0x42, ( ) - ' at 0x44 to 0x47, space 0x50). quest035 is the placeholder QUESTMAP34.
- Armies and battles: army files udNNN are placed by events (AppearUnit, AppearUnitEx, AppearUnitOld with the name second, PreloadUnit, PreloadUnitList). A battle's events are listed in evdata.dat (basedata.ar; also top 553), identical on both editions: records of a byte count, a word with the event number in its top 16 bits and the battle in the low 16 (0 for every battle), then the count of words that follow (condition type and arguments). Events in the same archive as the event with LaunchBMap(battle, map file) belong to that battle too. Army numbers are not battle numbers (quest 6 = army 371, story mission 9 = army 65). 159 of 275 armies match one or two battles.
- Battle selection: each story mission and quest record (from `0x0046D8F0`, battle number in bits 12 to 23 of the first word) names the battle a sortie loads; quests use 100 and up. Quest records are 52 bytes from `0x0046D9E0`, 218 of them (second word 1), 45 with a battle (100 to 143 and 200); the same on both editions. The Live page's Next sortie loads writes every record's battle number and puts the words back on request. The battle's event data then names its map archive (`bmapNNN.ar` for story battles, `qmapNNN.ar` for quests) in folder `bmap`. Changing a record's battle number through PINE at the base loads that whole battle, terrain, units and events: quest 6 loaded story battles 13, 31 and 9. Folder entries are 12 bytes (27-bit name hash and folder number, sector, size); matched by size, `bmapNNN.ar` files are top archives in disc order, such as battle 13 = 3712, quest 6 (qmap005) = 3677, mission 1 (bmap026) = 3701.
- Map events: a table of pointers at `0x0051D910` holds every battle's event conditions (low 16 bits of the first word = battle number, then the argument count and the condition type). Type 1 conditions are spots: menu kind, unit (0 for any), x, y. The action menu reads the spot under the unit (`0x001F2CD0`, kinds switched at `0x0038CB54`). Terrain kind 20 tiles are open gateways, not locked gates; locked gates are 100 HP units of class A5 with a kind 8 event.
- Script writing: ScriptWriter writes parsed scripts back to bytes; every event on both discs writes back byte for byte (numbers 12 bytes, texts with at least one zero padded to 4 and that length first, variables 12 bytes, event header word 0). Values change by their place among the event's numbers (ScriptValues); each copy (ev_all.ar for events 1 to 1000, plus top archives) is rewritten in place through ArchiveEditing, which refuses a script larger than its stored size. Recompression frees a median 8 bytes; archives holding events have a median 772 bytes of sector slack for later growth. Checked in game: event 3276 with turn 5 changed to 3 brought ud370 unit 4 on turn 3 from an exported disc.
- Archive repacking: archives are laid out as header, table, files in table order (each at the end of the one before plus 4, rounded down to 4), then the names; the third table word is the low 27 bits of the name hash. Every archive with events lays out again to its own bytes. Top-level archives sit back to back, each followed by zero padding to the next sector; after the last one DATA3.DAT is unused (English 91.7 MB of zeros, Japanese 81 MB of 0x80). The tables read at fixed places are in tops 14 (basedata.ar, before ev_all.ar), 553, 546 and 547, which are never moved. Checked in game: quest 6's archive (top 3413) moved from sector 411330 to the free sector 477360 with every event stored uncompressed (3,028 to 7,948 bytes); the battle opened and played, and the reinforcement set to turn 4 arrived on turn 4.
- Script lines: commands can be added, copied, removed and moved (ScriptLines, by path of argument and place from the event); new commands are accepted only with argument counts seen on the disc (ScriptLines.ArgumentCounts). Projects keep changed events whole (format version 3, with the SHA-256 of the disc's original). Checked in game: AppearUnit(5, "ud370", 1, 5, 21, 5, 19, 0) added after run event 3277 under quest 6's turn 2 brought ud370 script 5 to 5, 19 on turn 2.
- Script text: ScriptCompiler reads the Events page text back (indent levels, event line, assignments, if, else, while, condition blocks, multi-line calls with { } blocks, Name [hex] data, fully parenthesized expressions, escaped texts). To make the text reversible: texts escape backslash, quote, CR, LF and tab; minus on a plain number shows as -(5); an empty else is shown. All 3,983 events on both discs compile from their text to the original bytes.
- Shops: built by event scripts with MachiShopCreate(kind), then MachiShopAddItem(item) (always), MachiShopAddItemStock(item, stock) (stock refilled by event 123, which asks TownShopGetSuppliedQuantity(item, turn) for each stock number and runs event 126) and MachiShopAddItemEvnet(item, event) (runs the event when bought, as 3523 sets flag 970). 24 shops with items, the same on both discs: 13 at the base (events 546 to 937, placed by SetPeopleEx with the shop's event, as event 950 places 937 and 935) and 11 on battle maps, reached from a spot event that runs BMapTownExec(0, scene), where SetPeopleEx places the shopkeeper (battle 112: spot event 3403, scene 3404, shop 3405). Events 616, 723, 732 and 736 create shops without items (smithing and synthesis).
- Titles on the Japanese disc: its mission and quest titles are not in the unit-name font (decoding gives noise), so the English titles (reference/titles.csv, 230 entries read from the English disc) are used by entry name; the entries are numbered the same on both editions.
- Map files: folder `bmap` holds 83 map archives named `bmapNNN.ar`, `qmapNNN.ar` and `zmapNNN.ar` (found by the folder's name hashes), the same on both editions. Battles name their map in LaunchBMap(battle, file) or, for the title screen demo (battle 201, `zmap002.ar`), LaunchBMap2(mode, battle, file); 43 files are used. 18 quests listed in the quest records (such as quest 2, Looters) have no event that sets their quest number or starts a battle, so they are never offered; `maptest.ar` (battle 9999) is not on the disc.
- Map pictures: each map archive holds the picture as 8-bit TTX0 textures of 256 by 256 named by page (row times 8 plus column), header: format 0x13, pixel byte count, width, height, palette byte count 1024; RGBA palette stored with the second and third groups of 8 swapped in every 32. The hex grid is painted into the picture: columns 40 pixels wide, rows 35 high, odd columns half a row lower, starting at the picture's top left corner (fitted against the hex lines the game draws, in a PCSX2 capture of quest 6). 36-pixel rows looked right on the first rows but drift a pixel per row.
- Map layers: the `map` file starts with 16 layers of 0x2014 bytes (header with a flag and the width and height of texture `lNN.ttx`, then a 64 by 64 grid of 16-bit cells from 0x18 + layer times 0x2014). A cell with the top bit set takes tile (cell & 0x7FFF), 40 by 35 pixels, counted in rows across the texture, and covers the picture at column times 40, row times 35 (not staggered). The terrain grid follows at 0x20144. Layers hold the moving water (the base picture has rough placeholders there) and later changes such as the broken bridge of story battle 9 (layers 10 to 12). Scripts switch layers with DisplayLayer (0x2D1) inside an animation started by CreateBackGroudTree (0x2D2); a battle's opening event starts it (battle 9: event 2463 starts 2470, which shows layers 4 and 7 first; event 2466 switches to the broken bridge). Checked against a PCSX2 capture of quest 6: the composed picture matches the game's own.
- Start positions: after the terrain grid, x bytes from 0x22144 and y bytes from 0x22544, 16 placement groups of 64 slots, 0xFF for none; slot 0 of each group lies on the border and is not used. Group 0 holds the player's deployment hexes (quest 6: 7, matching SetMapUnitMax(7)). The battle's type 13 map events place army files with AppearUnitEx("udNNN", team, group, ...): unit n of the file at slot n + 1. Team 0 is the player's side, 1 the enemy, 2 and 3 other armies. Units without a slot are placed later by AppearUnit(id, file, team, from x, from y, to x, to y, flag), where id is the unit's script number at record offset 0x0C (often its name number; reinforcements have small numbers). Checked in a running game on quest 6: all 13 units of army 371 and the 5 player units at their slots.
- Reinforcements: AppearUnit(id, "udNNN", team, from x, from y, to x, to y, flag) and AppearUnitOld(id, "udNNN", team, x, y, flag) in a battle's other map events (and events they run) bring in the unit whose script number is id; when several units share the number, each call takes the next. The turn is in the script: a value set from GetCurrentTurn or GameGetTurn compared with == around the call (quest 6: event 3276, ud370 units 4 to 7 on turns 5 to 8). Turn tests joined with "and" and ranges (>=, >, <=, <) are read too; any other test (event flags, unit states, turns the battle stores with BMapGetVar) marks the arrival conditional. Arrivals in a spot event (type 1) name the spot. Over all battles, both editions: 406 arrivals, 316 on one turn, 16 over a range of turns (battle 12: unit 2 of ud083 each turn 2 to 21 while a flag is set), 18 from spots, 56 from other events (types 5, 6, 17, and type 11 events with stored turns), 125 conditional. Map event types read from quest 6's events: 8 (unit) runs when that unit is defeated and 19 (unit) when it is captured, with 0 for any of your units (both then check whether you have units left); 7 (character, unit, 0, message) shows a battle conversation; 11 (0, 1), one per battle, runs at the start of every turn; 13 runs as the battle opens; 1 is a spot. 5 (speaker, listener) runs when one unit talks to another (script numbers, 0 for any of yours; battle 24: 83 to 1365, quest 9 event 3519 turns the listeners with Betray). Types 6, 17 (army, one bit from 256 to 32768; no map cell carries those bits, so likely event flags), 28 and 31 are not yet understood. Checked live: quest 6 turn 5 brought ud370 unit 4 (script number 4) to 2, 1 as read from event 3276. Of the arrivals without a turn or spot, 29 come from the every-turn event (turns the battle stores, such as BMapGetVar) and 27 from types 5, 6, 7 and 17. Seven arrivals come from army file 001, the recruitable characters' own records (script number at the same offset): Paramythis (battle 6), Lynette (12), Larentia (21), Izerna, Dean, Elbert and Christine (26). Not yet watched arriving in a running game.
- Live unit list: the earlier filter required the script number to equal the name number, which hid many story enemies and reinforcements; the name number is at record offset 0x0E (0x0A in memory, without the tag).
- Silence, earlier attempts: with `0x001C365C` set to 1 the game still stored 9, also when written at the base before any battle code had run, so this was not PCSX2 keeping compiled code. The counting wait is set later at `0x001DF674` (above).
- Furniture shop list: the lines are fixed texts 91 to 103 in smenui.ar (top 14), one per piece in order of price, with the price written in as 16-bit glyphs (English: price first, digits 1 to 9 = 53 to 61, 0 = 62, space 4; Japanese: price last after spaces, digits 0 to 9 = 47, 1, 7, 12, 17, 22, 27, 32, 37, 42 from the font's own order, space 0). Found by comparing RAM with the list closed and open; checked live by writing new prices into the loaded text.
- Live writes: the game moves item lists after fights, so a live tool must find item slots again through the unit (+0x7C) before putting them back.
